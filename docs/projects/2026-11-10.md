# Travailler sur un système IOT de A à Z

## But du projet
Dans le cadre d'un projet éducatif en équipe ayant pour but de concevoir un système autonome à intégrer sur un fauteuil roulant basique, nous devions structurer l'architecture logicielle et électrique embarquée pour capter des données spécifiques contenues dans un cahier des charges comme la localisation GPS, le rythme cardiaque ou encore la détection de chutes. Nous sommes partis sur une approche modulaire : chaque sous-système est développé indépendamment avant d'être centralisé sur un contrôleur unique, capable de restituer les données sur une interface web.

## Ma position au sein du projet
Travaillant sur la partie localisation GPS, je dois fournir un module embarqué fiable capable d'acquérir la position géographique et la vitesse du fauteuil en temps réel, puis d'exposer ces données sur le réseau local pour qu'elles soient consommées par l'interface web de supervision.

!!! note

    Le développement de cette brique s'est appuyé au départ sur une base open-source ([GPS_ESP32](https://github.com/johannajes/GPS_ESP32/tree/main)), que j'ai ensuite adaptée et enrichie pour répondre aux contraintes du projet (parsing de trames RMC avec vitesse, buffer circulaire, gestion d'identifiant de session, support CORS et reconnexion Wi-Fi automatique).

## Choix de la stack technologique

Contrairement à un prototypage rapide sous Arduino, nous avons fait le choix d'un environnement industriel plus proche des contraintes réelles de l'embarqué.

### -> *Langage C & ESP-IDF*

Le firmware est développé en **C** avec le framework officiel d'Espressif (**ESP-IDF**, compilé via CMake). Cela permet de garder un contrôle fin sur la gestion mémoire, les périphériques matériels (UART, GPIO) et la pile réseau TCP/IP de l'**ESP32**.

### -> *FreeRTOS*

Intégré nativement à ESP-IDF, **FreeRTOS** permet de découper le programme en tâches concurrentes indépendantes avec des niveaux de priorité distincts : lecture série du GPS d'un côté, serveur HTTP et surveillance du Wi-Fi de l'autre, sans bloquer l'acquisition des données.

### -> *Protocole NMEA & API REST JSON*

Le module GPS communique en série via des trames standardisées **NMEA 0183**, tandis que l'ESP32 agit comme un micro-serveur web exposant une **API REST** légère au format **JSON** directement exploitable par le frontend.

## Architecture technique

Le code source du firmware est structuré dans le répertoire `main/` autour de trois modules principaux :

- `app_main.c` : point d'entrée qui initialise le matériel et orchestre le lancement des tâches FreeRTOS.
- `uart_read.c` : communication série avec le récepteur GPS, décodage des trames NMEA et gestion du témoin lumineux.
- `http_server.c` : connexion Wi-Fi en mode Station, stockage tampon des positions et serveur HTTP embarqué.

### Point d'entrée et orchestration : *app_main.c*

Au démarrage du microcontrôleur, la fonction `app_main()` prépare l'environnement matériel avant de déléguer le travail aux tâches temps réel :

-> **Initialisation GPIO** : configuration de la broche `GPIO_NUM_18` en sortie pour piloter une LED d'état (éteinte par défaut tant qu'aucun signal satellite valide n'est capté).

-> **Réseau Wi-Fi** : appel à `wifi_init_sta()` pour connecter l'ESP32 au réseau local, suivi de `start_wifi_monitor()`.

-> **Configuration UART1** : installation du driver `UART_NUM_1` à **9600 bauds** (8 bits de données, sans parité, 1 bit de stop) sur les broches `RXD2` (GPIO 4) et `TXD2` (GPIO 5) avec un buffer de `1024` octets.

-> **Lancement des tâches FreeRTOS** :
```c
xTaskCreate(uart_task, "uart_task", 4096, NULL, 10, NULL);
xTaskCreate(start_http_server, "start_http_server", 4096, NULL, 5, NULL);
```
La tâche d'acquisition GPS (`uart_task`) dispose d'une priorité supérieure (`10`) à celle du serveur HTTP (`5`) afin de ne jamais manquer de trames entrantes sur le port série.

### Acquisition et décodage GPS : *uart_read.c*

Le module GPS envoie en continu des trames textuelles sur l'interface UART1. La tâche `uart_task` lit ce flux toutes les secondes et recherche les phrases `$GPRMC` (ou `$GNRMC` selon les constellations reçues).

!!! info

    Une fonction `parse_gpgga()` est également présente dans le module pour traiter les trames GGA (qualité du fix), mais le système exploite principalement `parse_gprmc()` car la trame **RMC** (*Recommended Minimum Navigation Information*) fournit à la fois le statut du signal, les coordonnées et la vitesse de déplacement.

**Cycle de traitement d'une trame dans `parse_gprmc()` :**

-> Découpage de la chaîne NMEA via `strtok()` en utilisant la virgule comme délimiteur.

-> Vérification du champ statut (3ème champ) : si la valeur est différente de `'A'` (*Active*), la donnée est ignorée et la LED sur `GPIO_NUM_18` reste éteinte.

-> Extraction de la latitude (4ème champ), de la longitude (6ème champ) et de leurs indicateurs hémisphériques (`N/S`, `E/W`).

-> Conversion du format NMEA (`DDMM.MMMM`) vers des **degrés décimaux** exploitables sur une carte web :
```c
float parsed_lat = ((int)(lat / 100) + (lat - ((int)(lat / 100) * 100)) / 60.0) * (lat_dir == 'S' ? -1 : 1);
float parsed_lon = ((int)(lon / 100) + (lon - ((int)(lon / 100) * 100)) / 60.0) * (lon_dir == 'W' ? -1 : 1);
```

-> Conversion de la vitesse (8ème champ) exprimée en nœuds vers des **km/h** (`speed_knots * 1.852f`).

-> Allumage de la LED d'état et enregistrement du point via `update_gps_data(latitude, longitude, speed)`.

!!! tip "Mode simulation intégré"

    Pour permettre le développement de l'interface web en intérieur (là où le module GPS ne capte aucun satellite), une tâche alternative `uart_task_test()` génère des coordonnées aléatoires (autour de `60.1699, 24.9384`) et une vitesse simulée toutes les 2 secondes.

### Connectivité Wi-Fi et serveur REST : *http_server.c*

#### Gestion de la connexion et résilience

La fonction `wifi_init_sta()` initialise la mémoire flash non volatile (`nvs_flash_init`), configure l'ESP32 en mode Station (`WIFI_MODE_STA`) et désactive le mode économie d'énergie (`WIFI_PS_NONE`) afin d'éviter toute latence lors des requêtes HTTP. Une fois l'adresse IP attribuée par le serveur DHCP, elle est affichée dans la console série pour faciliter l'identification de la carte sur le réseau.

En parallèle, une tâche de supervision (`check_wifi_connection`) vérifie toutes les 5 secondes l'état de la liaison via `esp_wifi_sta_get_ap_info()` et relance automatiquement `esp_wifi_connect()` en cas de déconnexion.

#### Historique circulaire et API HTTP (Port 80)

Afin d'éviter toute fuite mémoire ou saturation de la RAM de l'ESP32, les positions sont stockées dans trois tableaux statiques dimensionnés à `MAX_COORDINATES = 100`. Lorsque le tableau est plein, la fonction `update_gps_data()` décale les valeurs existantes (fonctionnement FIFO) pour conserver uniquement les **100 derniers relevés**.

Le serveur HTTP (`esp_http_server`) expose trois gestionnaires sur l'endpoint `/gps` :

| Méthode | Handler | Rôle |
| :--- | :--- | :--- |
| **`GET /gps`** | `gps_data_handler` | Renvoie l'identifiant de session et l'historique des 100 dernières positions au format JSON. |
| **`POST /gps`** | `gps_post_handler` | Permet d'injecter manuellement un couple `latitude` / `longitude` en JSON pour les tests. |
| **`OPTIONS /gps`** | `cors_options_handler` | Répond aux requêtes *preflight* CORS (`GET, POST, OPTIONS`). |

Lors du premier appel `GET`, un `session_id` aléatoire à 6 chiffres est généré et conservé jusqu'au redémarrage de la carte, permettant au client web de détecter une réinitialisation du trajet. La réponse JSON renvoyée prend la forme suivante :

```json
{
  "session_id": 482910,
  "data": [
    {"latitude": 48.856613, "longitude": 2.352222, "speed": 4.20}
  ]
}
```

!!! info "Gestion des en-têtes CORS"

    L'interface web étant hébergée séparément de l'ESP32, les réponses incluent systématiquement l'en-tête `Access-Control-Allow-Origin: *` afin d'autoriser les requêtes `fetch` depuis le navigateur sans blocage de sécurité.

#### Sécurisation des identifiants Wi-Fi

!!! warning

    Pour ne pas exposer en clair le SSID et le mot de passe du réseau sur le dépôt Git public, le fichier `main/include/wifi_credentials.h` est ignoré via `.gitignore`.

Le fichier `wifi_config.h` utilise la directive C `__has_include("wifi_credentials.h")` : si le fichier local existe, il charge `SECRET_WIFI_SSID` et `SECRET_WIFI_PASSWORD`, sinon il bascule sur des valeurs par défaut. Un fichier modèle `wifi_credentials.h.exemple` est fourni dans le dépôt pour simplifier la configuration par les autres membres de l'équipe.

## Vue d'ensemble du projet et Conclusions

### Difficultés rencontrées et apprentissages
- **Tests en intérieur** : l'impossibilité d'obtenir un fix satellite dans les salles de cours a nécessité la mise en place d'un mode de simulation (`uart_task_test`) et d'une route `POST /gps` pour ne pas bloquer l'intégration avec l'équipe front-end.
- **Découpage temps réel** : la prise en main d'ESP-IDF et de FreeRTOS a permis de comprendre l'importance de la gestion des priorités de tâches et de l'allocation mémoire statique/dynamique sur microcontrôleur.
- **Communication inter-origines (CORS)** : l'interrogation directe d'un microcontrôleur depuis une application web moderne impose de gérer explicitement les requêtes `OPTIONS` et les en-têtes CORS côté C.

### Bilan

!!! success "Objectifs atteints sur la brique GPS"

    Le module GPS embarqué sur ESP32 est fonctionnel : il décode les trames NMEA en temps réel, signale l'acquisition satellite via une LED matérielle, maintient un historique glissant des 100 dernières positions et les met à disposition sur le réseau local via une API REST JSON.

### Axes d'amélioration
- **Centralisation multi-capteurs** : fusionner cette brique avec les modules de fréquence cardiaque et de détection de chute sur un même bus ou une même API unifiée.
- **Transport temps réel (WebSockets / MQTT)** : remplacer le *polling* HTTP périodique par du MQTT ou des WebSockets pour réduire la charge réseau et améliorer la réactivité des alertes (notamment en cas de chute).
- **Sécurisation des échanges** : ajouter une authentification par token ou chiffrer les flux si les données de santé et de localisation venaient à transiter hors du réseau local.
